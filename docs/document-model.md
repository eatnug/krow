# Document Model

Start at [Design Notes](README.md). Next: [Templates](templates.md).

krow documents are Markdown with fixed labels.

Natural-language content can be written by people or agents, but the document structure must be deterministic enough for code to generate, parse, retrieve, and validate.

## Stable IDs

Use stable ids for important units:

```text
Glossary Term
System Document
System Statement
Work Doc
Task
Review
```

Names are human labels. Stable ids are machine addresses that survive ordinary renames and file movement.

Examples:

```text
TERM:user.free
DOC:daily-recommendation-access
STMT:daily-recommendation-access.001
WORK:free-user-daily-recommendation
TASK:free-user-daily-recommendation.001
REVIEW:free-user-daily-recommendation
```

## Glossary

Glossary is the official vocabulary contract.

It identifies project terms, what they point to, what they do not point to, and which aliases are accepted. It does not try to describe all business or system behavior.

Term kinds:

```text
Noun
Verb
State
Rule
```

Glossary term v0 shape:

```md
## Free User

ID: TERM:user.free
Kind: Noun
Status: Approved

Meaning:
A User whose Subscription state is Free.

Boundary:
Does not include Paid User.
Trial User is not included unless explicitly defined.

Aliases:
- Free Subscription User
- Unpaid User

References:
- data: db/subscriptions
```

Required fields:

```text
ID
Kind
Status
Meaning
```

Optional fields:

```text
Boundary
Aliases
References
```

Status values:

```text
Proposed
Approved
Deprecated
```

## System Model

System Model is the current software description written with Glossary terms.

It is not a line-by-line natural language translation of code. It describes implemented meaning: behavior, rules, states, interfaces, responsibilities, and important boundaries.

Good statements:

```text
Free User cannot view Daily Recommendation.
Daily Recommendation access is decided from Subscription state.
Blocked User sees Upgrade Prompt.
```

Bad statements:

```text
This function checks user.subscription in an if statement.
If the condition is false it returns null.
Then it calls renderPrompt.
```

## System Documents

System Documents live under one folder:

```text
.krow/system/docs/
```

`Kind` is a light classification tag, not a complete ontology.

Default kinds:

```text
Capability
  A feature, behavior, or flow the system provides.

Shared Rule
  A condition, policy, limit, invariant, or access rule reused across behavior.

Shared Structure
  An important state, data, lifecycle, or relationship structure reused across behavior.

Responsibility Area
  A code or system responsibility boundary that matters for implementation.
```

Default to `Capability` when the document describes behavior or a flow. Split out `Shared Rule`, `Shared Structure`, or `Responsibility Area` only when that explanation is reused, repeated, or important enough to deserve its own document.

Document boundaries do not need to solve every ambiguous case upfront. When a topic can be described from two directions, choose the document that best matches the current work. If the choice matters for future work, record a short `Notes` entry instead of adding a new document type.

System Document v0 shape:

```md
# Daily Recommendation Access

ID: DOC:daily-recommendation-access
Kind: Capability
Status: Approved

Summary:
Describes how Users access Daily Recommendation.

## Statements

### Free User cannot view Daily Recommendation

ID: STMT:daily-recommendation-access.001
Status: Approved

Statement:
Free User cannot view Daily Recommendation.

Terms:
- TERM:user.free
- TERM:daily-recommendation

References:
- implementation: src/access/access-rule.ts
- verification: tests/daily-recommendation-access.test.ts
```

Required document fields:

```text
ID
Kind
Status
Summary
Statements
```

Optional document fields:

```text
Notes
```

Example note:

```md
Notes:
This document describes Daily Recommendation access behavior. Subscription state details can live in a separate System Document if they become large enough.
```

## System Statements

A System Statement is a current fact about the system, written with Glossary terms.

Required statement fields:

```text
ID
Status
Statement
Terms
```

Optional statement fields:

```text
References
Notes
```

Term-centered maps are derived views, not hand-maintained source documents. A future map for `TERM:user.free` can be generated by collecting all System Statements and Work Docs that mention that term.

## References

References are simple typed links from terms, documents, statements, Work Docs, or Reviews to concrete project material.

References v0 uses one-line Markdown entries:

```md
References:
- implementation: src/access/access-rule.ts
- verification: tests/daily-recommendation-access.test.ts
- interface: GET /api/recommendations/daily
- data: db/subscriptions
```

Default roles:

```text
implementation
verification
interface
data
```

No line numbers are required. Targets may be file paths, tests, routes, commands, schemas, tables, or other stable project locations.
